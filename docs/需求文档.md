# 云购生活数据仓库项目——需求文档

## 一、业务背景

云购生活（虚构）是一家全国连锁新零售企业，采用"线上商城 + 线下门店"融合经营模式，覆盖 15 个省份、60 家门店、8 大品类。2024 年全年积累约 11.5 万条业务数据（6 张表），但存在缺失、重复、异常、格式不一致、业务逻辑错误五类脏数据，管理层无法获得准确及时的经管分析。

## 二、业务痛点

1. 数据分散在多个业务系统，口径不统一；
2. 脏数据导致 KPI 不可信，营销决策依赖经验；
3. 缺少统一的数仓与可视化平台，报表靠人工汇总。

## 三、需求分析

### 3.1 功能需求

| 编号 | 需求 | 对应实现 |
|---|---|---|
| F1 | 6 张业务表统一采集导入 | ODS 层 6 表 |
| F2 | 五类脏数据清洗与质量报告 | clean_* 脚本 + 质量对比报告 |
| F3 | 四层数仓建模（ODS→DWD→DWS→ADS） | Hive 单库表名前缀分层 |
| F4 | 核心 KPI 计算（GMV/订单量/客单价/复购率） | ADS 层 `ads_core_kpi` |
| F5 | 多维度分析（品类/门店/省份/渠道/支付方式） | DWS 汇总 + EDA 简报 |
| F6 | 时间序列预测（未来 7 天 GMV） | predict.py 线性回归 |
| F7 | NL2SQL 自然语言查询 | nl2sql.py + DeepSeek API |
| F8 | 交互式仪表板与数据大屏 | Superset + ECharts |
| F9 | 一键部署 | Docker Compose |

### 3.2 非功能需求

- **可用性**：`docker compose up -d` 一键启动；
- **安全性**：API Key 与数据库密码通过 `.env` 注入，不入 Git；
- **性能**：核心查询带分区条件，单日查询 < 1s；
- **可复现**：全链路脚本化，按部署手册顺序可重跑。

## 四、指标体系

核心指标口径详见 `docs/指标口径对照表.md`，摘要：

- GMV：订单实付金额之和（排除 NULL）；
- 订单量：有效订单 14,398 / 全量 15,000 双口径；
- 客单价：2,508.45（有效）/ 2,407.78（含 NULL）；
- 复购率：100%（模拟数据构造特征，真实业务 20~40%）；
- 品类销售额：明细行口径，不可与 GMV 加总。

## 五、已知局限

1. 品类销售额与 GMV 口径不同，不可直接比较；
2. order_status 数字编码 1/2/3/4 按字典示例推断，待业务确认；
3. 大屏当前为离线快照数据，生产环境应直连 ADS 表。
